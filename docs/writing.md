# 글 쓰기

- `src/content/`에 글 작성
- 폴더 == 카테고리
- `draft가 false`일 때 배포환경에서 보임

---

## 1. 새 글 시작하기

**1.1 템플릿을 복사해 이름 변경**

```bash
cp src/content/_templates/post.md src/content/dev/2026-08-19-my-slug.md
cp src/content/_templates/review.md src/content/review/movie/2026-08-19-my-slug.md
```

리뷰는 템플릿이 따로 있다 — 사진 한 장과 `rating` 이 미리 들어 있다.

**1.2 Obsidian**
Obsidian에서 플러그인 '템플릿'을 켜고 템플릿 폴더를 `_templates`로 지정

## 2. 파일 위치와 이름

- 폴더 == 카테고리 (기본: dev, design, review, toon, travel, log)
- 기본 폴더를 추가하고 싶을 경우, `lib/categories.ts`에서 추가
- 파일명에서 날짜는 제외되어 url이 됨
- 확장자는 `.md` 와 `.mdx` 둘 다 된다. **`.md` 를 쓰는 게 낫다** — Obsidian 은
  `.md` 만 노트로 열고, 렌더 결과는 두 확장자가 완전히 같다 (본문을 컴파일하는
  쪽이 파일이 아니라 문자열을 받는다). 이미 쓴 `.mdx` 는 그대로 둬도 되고,
  바꾸고 싶으면 `git mv` 로 확장자만 갈면 된다 — 주소는 slug 가 정하므로 안 바뀐다
- 같은 글을 `.md` 와 `.mdx` 로 둘 다 두면 빌드가 멈춘다
- 폴더명을 화면에서 다르게 주고 싶을 경우 `lib/categories.ts`의 `CATEGORY_LABEL`에 적음
- **발행한 글도 그냥 이름을 바꾸거나 옮기면 된다.** 적을 표도, 외울 명령도 없다.
  옮기고 → `git add` → `pnpm index` 하면 옛 주소가 새 주소로 이어진다 (308)

  ```
  $ git add -A && pnpm index
    ✓ 이동 감지: dev/mdx-pipeline → dev/frontend/mdx-pipeline
    ✓ id-redirects.json 갱신 — 커밋에 같이 담을 것
  ```

  git 이 이름 변경을 기억하고(내용 유사도로 알아본다) `pnpm index`가 그걸 읽어
  `src/config/id-redirects.json`을 채운다. 갱신된 표는 커밋에 같이 담는다.
  손으로 열 일은 없다 — 되돌리면 저절로 지워지고, 날짜만 고치면 주소가 안 바뀌니
  아무 일도 안 일어난다

- **한 가지 조건: git이 이름 변경으로 알아봐야 한다.** 이름을 바꾸면서 본문을
  절반 넘게 갈아엎으면 git은 "지우고 새로 썼다"로 본다. 옮기는 커밋과 고치는
  커밋을 나누면 확실하다

## 4. 본문 문법

### 위키링크 — 글끼리 잇기

```md
[[2026-08-11-mdx-pipeline]] → 대상 글의 제목이 링크 문구가 된다
[[2026-08-11-mdx-pipeline|이 글에서]] → 문구를 직접 정한다
[[mdx-pipeline]] → slug 만 적어도 찾는다
```

Obsidian에서 `[[`를 치면 파일명이 자동완성되는데, 그걸 그대로 두면 된다.

- **한쪽에서만 걸어도 양쪽에 생긴다.** A에서 B를 링크하면 B의 "이어 읽기"에도 A가 뜨고,
  `/search`의 글 그래프에도 선이 하나 그어진다
- **가리키는 글이 없으면** 링크로 만들지 않고 원문 `[[...]]`을 그대로 둔다.
  빌드 로그에 `⚠ ... 위키링크가 가리키는 글이 없다`가 남지만 빌드는 통과한다
- 코드블록·인라인 코드 안의 `[[...]]`은 건드리지 않는다

### 콜아웃

Obsidian 문법 그대로다. 제목은 생략할 수 있다.

```md
> [!note] 참고
> [!tip] 팁
> [!danger] 경고
> [!quote] 인용
```

Obsidian의 나머지 종류(`info` `success` `question` `bug` `example` …)는 뜻이 가까운
네 개 중 하나로 접히고, 모르는 종류는 `note`로 떨어지며 로그에 남는다.
`warning` `attention` `caution`은 `danger`로 접힌다 — 주의와 경고를 색 두 개로
나눠 두면 쓸 때마다 어느 쪽인지 고르게 되어서 종류를 하나로 합쳤다.

콜아웃 안에는 문단뿐 아니라 목록·표·코드블록도 넣을 수 있다. 인용 기호(`>`)를
줄마다 붙이면 된다.

````md
> [!tip] 여러 줄 코드도 들어간다
> 앞뒤로 설명을 붙여도 된다.
>
> ```ts
> export function add(a: number, b: number) {
>   return a + b;
> }
> ```
````

### 그 밖

표(GFM) · 코드블록 · 목록 · 인용 · 수평선 전부 마크다운 그대로 쓰면 된다.

### 이미지

사진은 저장소에 넣지 않는다. Cloudflare R2 에 올리고, 본문은 파일 이름만 계속
가리킨다 — Obsidian 에서 보던 화면과 배포된 화면이 같은 글을 보는 셈이다.

1. 글이 든 폴더 아래 `_img/` 에 사진을 둔다 (Obsidian 설정 → 첨부 파일 기본
   위치를 "현재 폴더 아래 하위 폴더" · 이름 `_img` 로 두면 붙여넣기만 해도 여기
   떨어진다)
2. 본문에서 가리킨다. 두 문법 다 된다
3. `pnpm img` — 줄이고 webp 로 구워 R2 에 올리고, 주소를 `config/images.json` 에
   적는다. **이 파일은 커밋한다** (사진 원본은 `.gitignore` 가 막는다)

```md
![도톤보리의 밤](_img/dotonbori.jpg)

![[dotonbori.jpg]]
```

**밖에 걸린 주소를 그대로 써도 된다.** 이미 인터넷에 있는 사진이면 `pnpm img` 도
`_img/` 도 거치지 않는다 — 적은 주소가 그대로 나가고, 목록 썸네일도 그 주소를 쓴다.

```md
![대체 문구](https://example.com/poster.webp)
```

대신 두 가지를 내준다. 그 주소가 죽으면 그림도 죽고(우리 저장소에 사본이 없다),
크기를 미리 모르니 목록에서 사진이 뜰 때 그 줄이 한 번 밀린다. 오래 둘 사진은
`_img/` + `pnpm img` 쪽이 낫다.

`pnpm img` 를 돌리기 전에도 `pnpm dev` 에서는 원본이 그대로 보인다 (배포에는
나가지 않는 길이다). 안 올린 사진이 있으면 **빌드가 멈춘다** — 배포된 글에서
그림만 조용히 빈칸이 되는 것보다 낫다.

| 명령                 | 하는 일                                |
| -------------------- | -------------------------------------- |
| `pnpm img`           | 바뀐 것만 올린다                       |
| `pnpm img --dry-run` | 올리지 않고 무엇을 할지만 찍는다       |
| `pnpm img --force`   | 표에 있어도 다시 굽고 다시 올린다      |
| `pnpm img --prune`   | 어느 글도 안 쓰는 줄을 표에서 걷어낸다 |

알아 둘 것 몇 가지.

- 사진은 가로 1600px · webp 품질 80 으로 굽힌다. 아이폰 사진 한 장이 보통
  4MB 에서 200KB 안쪽이 된다
- 오브젝트 이름에 원본 내용의 해시가 붙는다. 사진을 고치면 이름이 바뀌므로
  캐시를 비울 일이 없고, 같은 사진을 두 글에서 쓰면 하나만 올라간다
- 두 언어판(`-slug.mdx` · `-slug.en.mdx`)은 같은 글이라 `_img/` 도 같이 쓴다
- 처음 한 번은 `.env.local` 의 `R2_*` 네 칸과 `NEXT_PUBLIC_IMAGE_BASE_URL` 을
  채워야 한다. 주소는 **R2 버킷에 붙인 커스텀 도메인**이다 — `r2.dev` 는
  개발용이라 캐시가 없고 속도 제한이 걸린다

## 4-1. 별점 · 썸네일

리뷰(`src/content/review/**`)는 frontmatter 에 별점을 적을 수 있다. 필수 다섯
개를 늘리는 게 아니라 리뷰에만 붙는 선택 칸이다 — 안 적으면 지금까지와 똑같이 선다.

```yaml
rating: 4 # 0~5, 0.5 단위 (3.5 처럼)
```

목록에서는 요약 아래, 글에서는 요약 다음에 별 다섯 개로 선다. 본문에 `★★★★` 나
`🟡🟡🟡🟡⚪` 로 적으면 글을 열어야만 보이는데, 목록에서 별점은 제목 다음으로
먼저 보는 값이라 칸으로 뺐다. review 밖에 적으면 `pnpm index` 가 거부한다.

**썸네일은 고르지 않는다.** 본문에 처음 나오는 사진이 곧 목록 왼쪽의 썸네일이다
(위키링크가 '이어 읽기'가 되는 것과 같은 결이다). 비율은 원본 그대로 줄여 걸고,
세로로 아주 긴 사진만 아래가 잘린다. 밖에 걸린 주소도 그대로 썸네일이 된다.
우리 사진인데 아직 `pnpm img` 를 안 돌렸으면 표에 줄이 없어서 목록에는 안 나온다 —
본문에서는 dev 에서 원본이 그대로 보인다.

## 5. draft — 쓰는 중인 글

`draft: true` 인 동안은

- **로컬에서만 보인다.** `pnpm dev`에서 목록에 "초고" 배지를 달고 나온다
- **프로덕션 색인에 아예 굽지 않는다.** 배포된 사이트에서는 URL을 직접 쳐도 404다.
  숨긴 게 아니라 없는 것이다

다 쓰면 `draft: false`로 바꾸고 push한다.

## 6. 확인하고 올리기

```bash
pnpm dev     # 파일 고치고 새로고침하면 바로 보인다 (watch 프로세스 없음)
pnpm index   # 검증 + 색인만 돌려 보기 (선택 — build 가 자동으로 한다)
```

`git push` 하면 배포 빌드가 `pnpm index && next build`를 돈다.
**검증에 걸리면 배포가 멈춘다.** 잘못된 글이 올라가는 것보다 낫다.

색인이 만들어지면 홈·카테고리 목록·아카이브·태그·검색·글 그래프·이어 읽기가
전부 따라온다. 손으로 갱신할 목록은 없다.

## 7. 빌드가 멈췄을 때

`pnpm index`가 파일과 이유를 같이 찍는다. 실제로 나오는 메시지들:

```
✖ 글 1편이 규약을 어겼다.

  travel/2026-05-05-osaka-3days.mdx
    tags: 태그는 2개 이상
```

| 메시지                                              | 뜻                                                |
| --------------------------------------------------- | ------------------------------------------------- |
| `Unrecognized keys: "related", "category"`          | frontmatter에 없는 칸을 적었다. 다섯 개만 남길 것 |
| `rating 은 review 카테고리의 글에만 적는다`         | 별점을 리뷰 밖에서 썼다                           |
| `별점은 0.5 단위로 적는다` · `별점은 5 이하`        | 별점 값                                           |
| `tags: 태그는 2개 이상` / `5개 이하`                | 태그 개수                                         |
| `tags: 태그는 소문자 영문 · 숫자 · 한글과 하이픈만` | 대문자·공백·특수문자가 섞였다                     |
| `태그는 카테고리명과 겹칠 수 없다`                  | `dev` `log` 같은 걸 태그로 썼다                   |
| `date: YYYY-MM-DD 형식이어야 한다`                  | `2026.8.11` 같은 표기                             |
| `summary: 요약은 200자를 넘기지 않는다`             | 요약이 길다                                       |
| `파일명은 YYYY-MM-DD-slug.md`                       | 날짜가 없거나 slug에 대문자·한글이 섞였다         |
| `... 가 두 번 있다 — .md 와 .mdx 로 둘 다`          | 같은 글이 확장자만 다르게 두 벌 있다              |
| `모르는 카테고리: xxx`                              | 여섯 폴더 밖에 파일을 뒀다                        |
| `... 가 두 번 있다`                                 | 같은 카테고리에 같은 slug가 둘                    |

경고(`⚠`)는 멈추지 않는다 — 깨진 위키링크, 파일명과 frontmatter의 날짜 불일치.

## 8. 원칙 (왜 이렇게 만들었는지)

- **글 길이에 하한이 없다.** 3줄 메모도 유효한 기록이다
- **공백기를 실패로 치지 않는다.** 정적 사이트라 방치 비용이 0이다
- **프로그램이 MDX 파일을 고치지 않는다.** 포매터도 `src/content`를 건드리지 않는다
  (`.prettierignore`). 정본은 언제나 사람이 쓴 그대로다
- **웹 에디터를 만들지 않는다.** 커밋에서 빌드까지 왕복이 로컬보다 느리다
