# 글 쓰기

`src/content/`가 곧 Obsidian vault다. 변환도, 업로드도, 웹 에디터도 없다.
파일을 만들고 → 쓰고 → `draft: false` → push. 그게 전부다.

---

## 1. 복붙 템플릿

`src/content/<카테고리>/YYYY-MM-DD-slug.mdx` 로 파일을 만들고 아래를 붙여넣는다.

````mdx
---
title: 여기에 제목
date: 2026-08-19
summary: 목록과 검색 결과, OG 설명에 그대로 나가는 한 줄. 200자까지.
tags: [태그하나, 태그둘]
draft: true
---

첫 문단. 여기부터 본문이다.

## 소제목

문단. **굵게** · _기울임_ · `인라인 코드` · [바깥 링크](https://example.com).

- 목록
- 항목

> [!note] 콜아웃 (제목은 생략해도 된다)
> 종류는 note · tip · danger · quote 네 개.

이어 읽을 글은 [[2026-08-11-mdx-pipeline]] 처럼 잇는다.
표시 문구를 바꾸려면 [[2026-08-11-mdx-pipeline|이렇게]].

| 표  | 도  | 된다 |
| --- | --- | ---- |
| a   | b   | c    |

```ts
const code = '코드블록도 된다';
```
````

## 2. 파일 위치와 이름

```
src/content/<카테고리>/YYYY-MM-DD-slug.mdx
            └ dev · design · review · toon · travel · log 여섯 개 중 하나

src/content/<카테고리>/<하위 카테고리>/YYYY-MM-DD-slug.mdx
                      └ 폴더를 더 파면 그대로 하위 카테고리가 된다
```

- **카테고리는 폴더가 정한다.** frontmatter에 `category`를 적으면 빌드가 거부한다
- **하위 카테고리도 폴더가 정한다.** 폴더를 만들고 글을 옮기면 좌측 네비에 바로 선다.
  등록할 곳도, 지울 곳도 없다 — 글이 하나도 없는 폴더는 메뉴에 나타나지 않는다.
  깊이 제한은 없고, 폴더 이름은 slug와 같은 규칙이다 (`page`만 못 쓴다 — 쪽 넘김이 이미 쓰는 말이다)
- **URL은 날짜를 뗀다** — `dev/2026-08-11-mdx-pipeline.mdx` → `/dev/mdx-pipeline`,
  `dev/nextjs/2026-08-20-app-router.mdx` → `/dev/nextjs/app-router`
- **slug는 소문자 영문·숫자·하이픈만.** 한글 slug는 안 된다
- **화면에 다른 이름으로 부르고 싶으면** `src/lib/categories.ts`의 `CATEGORY_LABEL`에 한 줄 적는다
  (`'dev/frontend/state': '상태 관리'`). 폴더 이름 = 주소, 이 표 = 화면에 나가는 이름이다.
  적지 않으면 폴더 이름을 그대로 쓴다. 이름만 바꾸는 것이라 주소는 안 바뀌고 링크도 안 깨진다
- **발행한 뒤에는 slug를 바꾸지 않는다.** URL이 곧 글의 주소이고, 바꾸면 밖에서 걸린 링크가 전부 깨진다.
  **폴더를 옮기는 것도 같다** — 이미 발행한 글을 하위 카테고리로 내리면 주소가 바뀐다.
  하위 카테고리는 새로 쓰는 글부터 쓰는 편이 안전하다 — 옮기면 옛 주소는 그대로 404다
  (`src/config/id-redirects.json`은 자리만 있고 아직 어디에도 연결돼 있지 않다)
- **카테고리를 누르면 그 폴더에 직접 든 글만 나온다.** 좌측 네비의 (n)도 같은 수다.
  `dev/frontend/react`의 글을 보려면 react까지 들어가야 한다 — 폴더를 여는 것과 같다.
  아래로 갈라지는 길은 목록 위의 하위 카테고리 칩과 좌측 네비의 `>`가 보여 준다

## 3. frontmatter — 다섯 칸이 전부다

| 필드      | 형식             | 규칙                                                                        |
| --------- | ---------------- | --------------------------------------------------------------------------- |
| `title`   | 문자열           | 비어 있으면 안 된다                                                         |
| `date`    | `YYYY-MM-DD`     | 따옴표 없어도 된다. 파일명 날짜와 다르면 경고(빌드는 통과)                  |
| `summary` | 문자열           | 1~200자. 목록·검색·OG 설명에 그대로 나간다                                  |
| `tags`    | 배열             | **2~5개.** 소문자 영문·숫자·한글과 하이픈. 카테고리명과 같은 태그는 못 쓴다 |
| `draft`   | `true` / `false` |                                                                             |

**여섯 번째 칸은 없다.** 다른 키를 넣으면 `pnpm index`가 이름을 대며 거부한다.
필드가 하나 늘 때마다 글 쓰기 전에 채워야 할 칸이 하나 느는데, 이 프로젝트에서
가장 큰 위험은 글쓰기 마찰이다.

이어 읽을 글(`related`)도 그래서 frontmatter에 없다 — 본문 위키링크에서 나온다.

## 4. 본문 문법

### 위키링크 — 글끼리 잇기

```md
[[2026-08-11-mdx-pipeline]] → 대상 글의 제목이 링크 문구가 된다
[[2026-08-11-mdx-pipeline|이 글에서]] → 문구를 직접 정한다
[[mdx-pipeline]] → slug 만 적어도 찾는다
```

Obsidian에서 `[[`를 치면 파일명이 자동완성되는데, 그걸 그대로 두면 된다.

- **한쪽에서만 걸어도 양쪽에 생긴다.** A에서 B를 링크하면 B의 "이어 읽기"에도 A가 뜨고,
  `/search`의 글 그래프에도 선이 하나 그어진다
- **가리키는 글이 없으면** 링크로 만들지 않고 원문 `[[...]]`을 그대로 둔다.
  빌드 로그에 `⚠ ... 위키링크가 가리키는 글이 없다`가 남지만 빌드는 통과한다
- 코드블록·인라인 코드 안의 `[[...]]`은 건드리지 않는다

### 콜아웃

Obsidian 문법 그대로다. 제목은 생략할 수 있다.

```md
> [!note] 참고
> [!tip] 팁
> [!danger] 경고
> [!quote] 인용
```

Obsidian의 나머지 종류(`info` `success` `question` `bug` `example` …)는 뜻이 가까운
네 개 중 하나로 접히고, 모르는 종류는 `note`로 떨어지며 로그에 남는다.
`warning` `attention` `caution`은 `danger`로 접힌다 — 주의와 경고를 색 두 개로
나눠 두면 쓸 때마다 어느 쪽인지 고르게 되어서 종류를 하나로 합쳤다.

콜아웃 안에는 문단뿐 아니라 목록·표·코드블록도 넣을 수 있다. 인용 기호(`>`)를
줄마다 붙이면 된다.

````md
> [!tip] 여러 줄 코드도 들어간다
> 앞뒤로 설명을 붙여도 된다.
>
> ```ts
> export function add(a: number, b: number) {
>   return a + b;
> }
> ```
````

### 그 밖

표(GFM) · 코드블록 · 목록 · 인용 · 수평선 전부 마크다운 그대로 쓰면 된다.

**이미지는 아직 안 된다.** R2 업로드 스크립트(`pnpm img`)가 미작성이라,
지금 이미지를 넣으면 깨진 링크가 된다.

## 5. draft — 쓰는 중인 글

`draft: true` 인 동안은

- **로컬에서만 보인다.** `pnpm dev`에서 목록에 "초고" 배지를 달고 나온다
- **프로덕션 색인에 아예 굽지 않는다.** 배포된 사이트에서는 URL을 직접 쳐도 404다.
  숨긴 게 아니라 없는 것이다

다 쓰면 `draft: false`로 바꾸고 push한다.

---

## 6. 확인하고 올리기

```bash
pnpm dev     # 파일 고치고 새로고침하면 바로 보인다 (watch 프로세스 없음)
pnpm index   # 검증 + 색인만 돌려 보기 (선택 — build 가 자동으로 한다)
```

`git push` 하면 배포 빌드가 `pnpm index && next build`를 돈다.
**검증에 걸리면 배포가 멈춘다.** 잘못된 글이 올라가는 것보다 낫다.

색인이 만들어지면 홈·카테고리 목록·아카이브·태그·검색·글 그래프·이어 읽기가
전부 따라온다. 손으로 갱신할 목록은 없다.

## 7. 빌드가 멈췄을 때

`pnpm index`가 파일과 이유를 같이 찍는다. 실제로 나오는 메시지들:

```
✖ 글 1편이 규약을 어겼다.

  travel/2026-05-05-osaka-3days.mdx
    tags: 태그는 2개 이상
```

| 메시지                                              | 뜻                                                |
| --------------------------------------------------- | ------------------------------------------------- |
| `Unrecognized keys: "related", "category"`          | frontmatter에 없는 칸을 적었다. 다섯 개만 남길 것 |
| `tags: 태그는 2개 이상` / `5개 이하`                | 태그 개수                                         |
| `tags: 태그는 소문자 영문 · 숫자 · 한글과 하이픈만` | 대문자·공백·특수문자가 섞였다                     |
| `태그는 카테고리명과 겹칠 수 없다`                  | `dev` `log` 같은 걸 태그로 썼다                   |
| `date: YYYY-MM-DD 형식이어야 한다`                  | `2026.8.11` 같은 표기                             |
| `summary: 요약은 200자를 넘기지 않는다`             | 요약이 길다                                       |
| `파일명은 YYYY-MM-DD-slug.mdx`                      | 날짜가 없거나 slug에 대문자·한글이 섞였다         |
| `모르는 카테고리: xxx`                              | 여섯 폴더 밖에 파일을 뒀다                        |
| `... 가 두 번 있다`                                 | 같은 카테고리에 같은 slug가 둘                    |

경고(`⚠`)는 멈추지 않는다 — 깨진 위키링크, 파일명과 frontmatter의 날짜 불일치.

## 8. 원칙 (왜 이렇게 만들었는지)

- **글 길이에 하한이 없다.** 3줄 메모도 유효한 기록이다
- **공백기를 실패로 치지 않는다.** 정적 사이트라 방치 비용이 0이다
- **프로그램이 MDX 파일을 고치지 않는다.** 포매터도 `src/content`를 건드리지 않는다
  (`.prettierignore`). 정본은 언제나 사람이 쓴 그대로다
- **웹 에디터를 만들지 않는다.** 커밋에서 빌드까지 왕복이 로컬보다 느리다
